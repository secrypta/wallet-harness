# drain-bench - a labeled benchmark for wallet / approval-drain detection

> **Working name.** `drain-bench` / `secrypta/drain-bench` is a working title; the final
> public name is set at publication. Nothing in the dataset or scorer depends on it.

`drain-bench` is a small, **labeled, ground-truth** dataset of wallet/approval **drain**
cases plus a **tool-agnostic scorer**. You point any detector (a wallet policy, a static
analyzer, your own script) at the cases, write its verdicts in a simple text format, and
`score.sh` tells you precision / recall / F1 against the labels.

It is derived from the [`wallet-harness`](../README.md) corpus (frozen interface `v0.1`).
The fixtures, their labels, and their provenance are the corpus; drain-bench repackages
them as a standalone dataset anyone can score against without the wal test harness.

## What this is - and what it is NOT

- **It is:** an open dataset + scorer + methodology, published with **our own** tool's
  result and an honest disclosure about that result.
- **It is NOT** a public leaderboard of third-party tools. We do not publish per-tool
  scores for other people's tools. If you run your tool, the result is **yours** to
  publish or not (see *Run your own tool* below). A low score here does **not** mean a
  tool is bad - most tools were never designed to catch drain-UX (see *Scope caveats*).

## Dataset

155 labeled fixtures across **13 vectors** (70 `vuln` + 85 `safe`). Each fixture is a `vuln`
or `safe` case in one of three tiers (a vector may carry more than one case per tier):

| tier | what | label | why it is in the set |
|------|------|-------|----------------------|
| `a` (toy)      | an MIT toy pair we wrote (one vulnerable, one safe) | `vuln` / `safe` | fast mechanics smoke |
| `b` (incident) | a minimized reproduction of a **real public incident** | `vuln` | the detector must flag a real bug |
| `c` (safe)     | **genuinely safe** real code (e.g. OpenZeppelin), not a tweaked toy | `safe` | the real 0-false-positive test |

Each verdict is computed from the **measured on-chain outcome** of actually running the
vector (e.g. the victim's balance reaching zero), **not** from matching known attacker
addresses or from a hard-coded answer. Tier-b uses real incident addresses only for
fidelity; the verdict would be identical with placeholder addresses.

Ground truth and provenance live in each fixture's `meta` and `PROVENANCE.md` under
[`../fixtures/`](../fixtures/). Every tier-b real incident is summarized - date, chain, loss,
on-chain tx (or an honest `mechanism-level` note), and independent sources - in the
provenance index [`INCIDENTS.md`](INCIDENTS.md). The standalone, machine-readable index is
[`dataset/manifest.tsv`](dataset/manifest.tsv), regenerated by
[`tools/gen-manifest.sh`](tools/gen-manifest.sh):

```
vector  tier  target  label  split  test  source_dir  provenance
```

- **`label`** - ground truth: `vuln` ⇒ a detector should report `VULNERABLE`; `safe` ⇒ it
  should report `BLOCKED`.
- **`split`** - honesty marker, see below. Currently 58 `dev`, 18 `holdout`, plus an
  independent **external** cross-validation set (see *External cross-validation*).

The 13 vectors: approve-drainer, set-approval-for-all, permit-phishing, permit2-phishing,
signature-phishing, blind-eth-sign, address-poisoning, fake-airdrop, malicious-calldata,
delegatecall-hijack, create2-metamorphic, eip7702-delegation, upgrade-governance. Each has a human spec in
[`../corpus/`](../corpus/); the validation standard is
[`../corpus/real-cases.md`](../corpus/real-cases.md). Each spec carries a **Prior art** line
cross-referencing the nearest published category (e.g. transaction-phishing taxonomies,
DASP-10 / SWC) so the vectors are citable and not a taxonomy invented in a vacuum.

## Related work (positioning, not ranking)

Two kinds of public resource are adjacent to drain-bench, on **different axes**:

- **Transaction-level phishing detection** (ice-phishing / address-poisoning / NFT-order
  detectors, some integrated into monitoring networks) asks *"is this on-chain transaction
  phishing?"*, using address history and heuristics, and ships labeled **transaction** datasets.
- **Generic contract-bug benchmarks** (reentrancy, overflow, access-control, ... under
  taxonomies like DASP-10 / SWC) ask *"does this contract contain a known bug class?"*.

drain-bench sits on a third axis: *"does this wallet/contract **defense** hold against a drain
vector?"* - an offline, executable check pairing each vector with a vulnerable case, a
minimized real-incident repro, and a **genuinely-safe real implementation** scored for zero
false positives. We state the axis; we do not rank other projects.

## Honesty / disclosure - read before quoting any number

wal's own row comes from per-fixture Foundry tests written **together with each fixture** (dev
and holdout alike). So wal's own score on drain-bench is a **self-consistency check, not an
independent result**. Any public benchmark is
prone to overfitting, and this disclaimer applies to **every self-reported number on this
dataset, ours included**.

Concretely:

- **61 fixtures are `split=dev`** (non-independent): the wal tests were written and
  tuned against them, so their score is a sanity check, not evidence of generalization. We
  do **not** retroactively relabel any of them as a "holdout" and call them independent -
  that would be fake honesty.
- **94 fixtures are `split=holdout`** (41 `vuln`, 53 `safe`), covering **all 13 vectors**:
  each is a **new** case, added after the `v0.1` interface freeze and drawn from independently
  web-verified public incidents and real safe implementations (Anyswap/Multichain 2022, Pennysia 2026, Squid, Lixir, Parity, Audius,
  Tornado-governance, Inferno-7702, WBTC address-poisoning 2024, NFTTrader 2023,
  Bebop JamSettlement 2025, Hedgey 2024, Lumi/Sodium 2026, Odos 2025; and unmodified Solady
  ERC20 / ERC-721 / ERC-2612 permit / ERC-1271 / MerkleProof, OpenZeppelin ERC20Permit, and
  Uniswap Permit2 SignatureTransfer / SignatureVerification). It is independent ground truth
  for scoring **other** tools. It is not blind for wal itself: every holdout fixture got its own
  new Foundry test (85 test files were added under `test/` after `v0.1`), so wal's holdout 1.0 is
  the same self-consistency check as dev. Score it with `--split holdout`.
- **Nine vectors have an independent *vulnerable* holdout; four are precision-side (safe-only)**
  - the safe-only four are `permit2-phishing`, `fake-airdrop`, `blind-eth-sign` and
  `signature-phishing`. No clean, independent *vulnerable* public incident exists for these at
  our provenance bar (the one solid blind-sign incident, Bybit, is already the
  `delegatecall-hijack` case and is not reused; and the Bebop JamSettlement incident we
  examined for `signature-phishing` turned out, on verification, to be an
  arbitrary-caller-calldata drain with no victim signature at all, so it is labelled
  `malicious-calldata`, not reused as a signature case). Rather than invent one, their
  independent holdout is a **real safe** implementation the detector must stay silent on
  (0 FP) - an honest precision check, not a recall claim. Flagged in each fixture's
  `meta` / `PROVENANCE.md`. Read the score **per vector**, not just the headline.
- Read the two splits as two different claims: `dev` says "the tool reproduces its own
  corpus"; `holdout` says "the case is independent of the dev corpus" - a generalization signal for a
  tool that was not built on it, but not for wal's own row. **The corpus is
  hand-built and growing (currently 155 fixtures); `p/r = 1.0` demonstrates the method and the
  0-FP discipline on THIS corpus - it is not a statistical claim of generalization to wallets in
  the wild.** The
  holdout is a signal, not proof; it grows as new independent cases are found.

## External cross-validation (independent ground truth, split=external)

The strongest honesty check is a corpus **we did not label**. `bench/external/` runs our
tooling against third-party datasets whose ground truth is set by others, so the labels cannot
be a wal artifact:

- **SmartBugs-Curated** (`bench/external/smartbugs-curated/`, `access_control` category, 12
  contracts, upstream line-level annotations; license-clean files vendored with NOTICE, GPL
  ones referenced only). On the vectors inside our scope the scanner **agrees 9/9** with the
  upstream labels (R7/R8 delegatecall ×2; R12 init-hijack ×7), and on the 4 out-of-scope bugs
  (tx.origin, selfdestruct, logic) it stays **correctly silent, 0 FP / 0 in-scope FN**. We are
  **not** a general analyzer and do not lead on a general corpus - the value here is *agreement
  with an independent taxonomy* on the overlap plus honest out-of-scope silence.
- **SWC Registry** (`bench/external/swc-xval/`): SWC-112 -> R7 (2/3 match + 1 documented stricter
  threshold). SWC-121/122 have no registry example contract, so they are **not** cross-validated
  (we do not fabricate one).

`external` is a third, independent split, distinct from `dev` (where detectors were authored)
and `holdout` (new cases we authored post-freeze). See `bench/external/*/README.md`.

## Scoring

Write your tool's verdicts to a file, one line per scored target (any other lines ignored):

```
[<vector>] target=<target> verdict=<VULNERABLE|BLOCKED>
```

`VULNERABLE` = "the tool flagged a drain / unsafe action"; `BLOCKED` = "the tool judged it
safe / stayed silent". Mapping your tool's native output to this schema is a judgement call
- **document that mapping** next to your results; it is the easiest place to accidentally
inflate or deflate a score.

```
bench/score.sh <verdicts-file> [--manifest <path>] [--split dev|holdout|all] [--strict]
```

Scoring per `(vector, target)`:

| label | verdict    | cell | meaning                  |
|-------|------------|------|--------------------------|
| vuln  | VULNERABLE | TP   | real bug flagged         |
| vuln  | BLOCKED    | FN   | real bug missed          |
| safe  | BLOCKED    | TN   | safe code stayed silent  |
| safe  | VULNERABLE | FP   | false positive           |

A labeled fixture with no matching verdict line is a **coverage gap** (`MISS`): the tool
did not report on it. By default `score.sh` is **report-only** (it prints metrics and exits
0 - other tools legitimately produce FP/FN/MISS). `--strict` exits non-zero on any FP, FN,
or MISS, and is what wal's own CI uses.

## Scope caveats (why a low score is often not the tool's fault)

Most of these cases are **drain-UX / approval-flow** problems - a user is tricked into a
signature or an `approve`, or a front-end swaps a target. A general-purpose static analyzer
or a reentrancy linter was **not built to catch that** and will score low here. That is a
statement about task fit, not tool quality. Read the per-vector breakdown, not just the
headline.

## Run your own tool (and optionally share)

1. `bench/score.sh --list` shows the exact `(vector, target)` pairs to produce verdicts for
   (labels withheld - score blind). `bench/score.sh --template > my.verdicts` gives you a
   ready-to-fill file with one line per target.
2. Run your detector over the fixtures (sources are under [`../fixtures/`](../fixtures/)) and
   fill in each `verdict=` (VULNERABLE / BLOCKED).
3. `bench/score.sh my.verdicts` prints the confusion matrix, precision/recall/F1, **and an
   actionable list of exactly what you got wrong** (FP/FN/MISS). Add `--json` for a
   machine-readable result (CI), `--strict` to exit non-zero on any FP/FN/MISS.
4. *(optional)* Share your result via PR - add a `results/<tool>/` directory with the raw
   output, tool version, exact command, and mapping rule. See
   [`CONTRIBUTING.md`](CONTRIBUTING.md) for the layout and [`results/EXAMPLE/`](results/EXAMPLE/)
   for a complete runnable stub. It is **your** self-report, which we re-run and merge, not
   our rating of your tool.

## Our own result

wal's result is produced by running the wal harness and scoring its verdicts:

```
bench/tools/run-wal.sh            # runs the wal Foundry suite in Docker -> results/wal/verdicts.txt
bench/score.sh results/wal/verdicts.txt --strict
```

See the honesty section above before quoting it.

## Severity & rating

The dataset's ground truth is binary - each case is `vuln` or `safe`. **Severity is a
property a detector assigns, not a dataset label**, so the benchmark stays tool-agnostic
(any tool brings its own severity model). This keeps the honest line: the answer key says
*whether* a case is a drain, not *how bad* - the latter is the tool's call.
